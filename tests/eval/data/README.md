# tests/eval/data — validation datasets

Two input datasets, two output formats. See `report/VALIDATION_PLAN.md` for the methodology.

## Inputs (you fill these in)

| File | What it describes | Format & why |
|---|---|---|
| `proteins.yaml` | A flat list of L1 test cases. Each test case is one `(input_seq, context_question) -> expected top-5` triple, including the negative control. Canonical sequences are NOT duplicated here — they live on UniProt. | YAML — multi-line sequences and inline comments. |
| `llm_scenarios.yaml` | 2 frozen protein contexts (CTX_INSULIN, CTX_P53) + 10 scenarios with rubrics + judge LLM config. | YAML — multi-line `function_text` and rubric checks. |

Each file has at least one fully filled-in example block and `<FILL: ...>` placeholders for the rest.

## Outputs (generated by the harness, not committed except for a baseline)

Both produced as CSV — easy to load into pandas, easy to diff, easy to paste into the report table.

### `runs/<timestamp>/retriever_results.csv`

One row per test case.

| Column | Type | Example |
|---|---|---|
| `test_case_id` | string | `T03_P01308_V2` |
| `protein_ref` | string (UniProt accession or empty) | `P01308` |
| `variant` | string | `V2_point_mutations_3` |
| `context_question` | string | `Identify this protein and list close matches.` |
| `input_type` | string | `protein` |
| `expected_top1_any_of` | string (`\|`-separated, or empty) | `P01308` |
| `expected_must_appear` | string (`\|`-separated) | `P01308` |
| `top1_accession_before_rerank` | string | `P01308` |
| `top1_accession_after_rerank` | string | `P01308` |
| `top1_score` | float | `0.91` |
| `top5_accessions_after_rerank` | string (`\|`-separated, ordered) | `P01308\|P01325\|P01317\|P67972\|P30410` |
| `top1_pass` | int (0/1) | `1` |
| `top5_pass` | int (0/1) | `1` |
| `rank_of_expected_before_rerank` | int (1..50, or `-1` if not found) | `1` |
| `rank_of_expected_after_rerank` | int | `1` |
| `reciprocal_rank_at_5` | float | `1.0` |
| `latency_ms` | int | `842` |

Aggregation script reads this and prints the §2.4 metrics table.

### `runs/<timestamp>/llm_results.csv`

One row per (scenario, rubric item). 10 scenarios × ~3 items ≈ 30 rows.

| Column | Type | Example |
|---|---|---|
| `scenario_id` | string | `A1` |
| `class` | string | `A` |
| `context_id` | string | `CTX_INSULIN` |
| `question` | string | `What is the main biological function...` |
| `rubric_item` | string | `a` |
| `rubric_type` | string | `must_cover` |
| `rubric_check` | string | `Mentions the main function...` |
| `passed` | int (0 / 1) | `1` |
| `judge_explanation` | string | `Mentions glucose regulation and hormone signalling.` |
| `gemini_answer_path` | string (relative) | `llm_raw/A1.txt` |
| `judge_raw_path` | string (relative) | `judge_raw/A1_a.json` |

`gemini_answer_path` and `judge_raw_path` point inside the same run directory — raw responses kept for audit (§3.6).

## How to validate your fill-in

```powershell
python -m tests.eval.validate_data
```

This will:
1. parse both YAML files,
2. fail if any `<FILL: ...>` placeholders remain,
3. fail if any accession in `expected.top1_any_of` / `expected.must_appear_in_top5` or `metadata.protein_ref` in `proteins.yaml` is malformed (and that `top1_any_of` is a list),
4. fail if any `context_id` referenced by a scenario does not exist in `contexts`.

Run this BEFORE you commit the filled-in dataset — it's the cheapest way to catch typos.
